# Decisions

## Made (by the user)

| Decision | Choice |
|---|---|
| Approach | Own tool, not a paid or cloud service |
| Pose model | MediaPipe, **latest version** (1.2.0 at the time) |
| Where it runs | Inside Blender, as a Blender extension |
| Language (2026-11-03) | **All Python** (numpy for the math), so the extension is only Python + bundled wheels as extensions.blender.org expects. Replaces the first plan (thin Python add-on + C# core run as a subprocess, 2026-11-02). The build tools are Python too (2026-11-03) |
| Cameras | Single camera first; multi-camera later if it goes well |
| Privacy | Fully local, no third parties (see [PRIVACY.md](PRIVACY.md)) |
| Distribution | extensions.blender.org, installed from inside Blender in one step (2026-11-03) |
| Name (2026-11-03) | **FreeClipMocap**. The first name, BlendMotion, was taken. Checked free 2026-11-03: no extension on extensions.blender.org, no GitHub repo, no web hits. Close to the existing FreeMoCap project (noted to the user). The repo folder is `FreeClipMoCap` (renamed from `BlendMotion` by the user, 2026-11-03); the product keeps the spelling FreeClipMocap (the user) |
| Licence (2026-11-03) | **GPL-3.0-or-later** for the whole project (required for add-ons on extensions.blender.org) |
| Start | Workspace and docs only; implementation (Phase 0) later |
| Wheel downloads (Phase 0) | With Blender's own `python.exe`, not the standalone Python 3.15 |
| Scratch work | `Scratch/` in the repo (wheels, models, experiments) |
| Pose model variant | **Heavy** by default; lite and full offered as a fast preview (decided after the first real clip) |
| Re-solving | Every Solve makes a new Action (take): `Name`, `Name.001`, …, each with a fake user so Blender's cleanup on save keeps it; the newest is assigned to the armature |
| Landmark cache | One cache per video + model + capture settings (named with a short settings hash), in a FreeClipMocap folder next to the video; identical settings reuse it |
| Landmark cache format (2026-11-03) | **Binary**; the exact layout is proposed before Phase 1 code. (Bone rotations no longer need a file: the solver runs in the same Python as the keyframing.) |
| FBX export over an existing file | Blender's normal file dialog: red name, the user confirms the overwrite |
| MediaPipe telemetry | Keep 1.2.0 and patch the endpoint in `libmediapipe.dll` (first with `PatchMediaPipeTelemetry.cs`, now inside the Python wheel repack tool); building from source is revisited in Phase 3 |
| Bundled wheels | Only `mediapipe` and `opencv-contrib-python`. Dropped: sounddevice, cffi, pycparser, absl-py, flatbuffers, and matplotlib with its 9 dependencies. certifi and numpy come from Blender |
| matplotlib (2026-11-03) | Not bundled. The bundled mediapipe wheel gets a second patch: `drawing_utils.py` imports matplotlib inside `plot_landmarks` instead of at the top. (The earlier `sys.modules` stand-in broke the add-on guideline "Bundle Modules".) |
| Offline test | The user disconnects the internet and runs `Scratch/Phase0/scripts/offline_test.ps1` alone (not firewall rules). Passed 2026-11-02 |
| Video decoding (2026-11-03) | OpenCV for capture; Blender's movie clip only for showing the video in the Compare view |
| Target rigs (2026-11-03) | Versatile, best user experience: auto-guess the bone map from names and hierarchy → editable map in the panel → save/load maps as presets; built-in presets for Mixamo (Phase 1), Rigify, Auto-Rig Pro, … (Phase 2) |
| Export (2026-11-03) | From the panel: FBX (LifeInArena settings, Blender's built-in exporter) and BVH (our own writer, see "BVH export") |
| Python style (2026-11-03) | Same spirit as the C# rules; whenever a Python implementation choice comes up, ask the user |
| Multi-camera calibration (2026-11-03) | Python (OpenCV), the user's leaning; confirmed by the all-Python decision. The bundled OpenCV 5.0 has `aruco.CharucoDetector`, `calibrateCamera`, `calibrateMultiview` and `triangulatePoints` (checked 2026-11-03) |
| Calibration recording (2026-11-03) | **Any clip + frame range** (the user): Calibrate takes one video per camera and a frame range, so the board can be waved at the start of each take or filmed once in a calibration clip reused while the cameras stay put |
| Calibration board (2026-11-03) | **ChArUco 4×5 squares, 48 mm nominal, `DICT_4X4_50`, printed on A4/Letter** (the user), taped flat on cardboard cut flush with the paper's bottom edge; the extension saves the board image (A4 at 300 dpi, board centred); the user measures one square and enters its size in mm. Replaces the first choice of 5×7 at 38 mm: measured at 1080p, 2.5 m and 45°, 5×7 found 0 of 24 corners, 4×5 found 8 of 12, and two phones framing a whole body stand ~2.5–3 m from the middle. 48 mm instead of 50 mm leaves a printable margin on both A4 and Letter |
| Board on a screen (2026-11-03) | **Paper + Custom** (the user): the Paper menu offers A4, Letter and Custom; Custom shows a 'Below Squares' field, the distance in mm from the lowest row of squares to the edge standing on the floor (a tablet's bezel included), measured with a ruler. The same board image is shown full-screen. For paper the distance is half the paper's height left over by the squares. The calibration file stores this distance instead of the paper height (format version 2; older files are calibrated again) |
| Saved lenses (2026-11-03) | **In the user folder, by name** (the user): one JSON per lens in the extension's user folder (`lenses/`), shared by every project; each camera row in the Calibration box has a Lens menu (Measure, or a saved lens). **Made from a calibration** (the user): Save Lens stores that camera's refined lens from the last calibration under a typed name. **Kept fixed** (the user): only the cameras' poses are fitted, so no close-ups are needed. A lens is refused for video of another size. Claude: the menu stores the lens name (not the menu position), a deleted lens shows as '(missing)' and Calibrate refuses it; a saved lens and a measured one together: both refined first, then the pose fitted with the saved lens restored and both fixed (OpenCV fixes both lenses or neither); the saved lenses are part of the calibration's inputs, so changing one calibrates again |
| Typed focal length (2026-11-03) | **'Typed' in the Lens menu** (the user): a camera's focal length in mm, **35 mm equivalent across the video's longer side** (the user; the same conversion as Compare View's Lens and the Blender phone cameras, shared as `constants/camera_lens.py`), with a **Keep Fixed checkbox per camera** (the user): on, exactly that focal length with no distortion and no close-ups needed; off, the starting point that the board corrects (the lens measured from the close-ups starting there, or without close-ups refined by the camera pair fit). Each camera row shows the last calibration's focal length in mm. Claude: the lens settings of camera 1 and cameras 2+ come from one mixin class, as Blender's `ExportHelper` does |
| Calibration from the body (2026-11-03) | **A second method next to the board** (the user): Method Board / Body in the Calibration box. Body: the actor walks around both phones' view; each video's landmarks (captured first if needed, the same cache the take uses) are matched between the views. **Scale from the measured distance between camera 1's and camera 2's lenses** (the user; 'Phones Apart'). **Lenses typed or saved, always kept fixed** (the user chose an option to let the body refine the focal length; Claude dropped it after the synthetic test: with both phones aimed at the actor from about the same height the views fit equally well at very different focal lengths, and the refinement ran to 2.5× the true value). **Floor from the planted feet** (heels and toes still for a moment, a plane fitted when they spread over the floor, otherwise the body's shoulders-over-ankles direction). The take's own videos or separate ones, as for the board. Method chosen by Claude: 16 body joints (shoulders to toes) with visibility ≥ 0.5, camera 2's joints interpolated to camera 1's frame times; essential matrix with RANSAC; the sound offset refined within ±60 ms on moving joints (Sampson distance); frames where one phone swapped left and right are swapped back; cameras 3+ placed by PnP on the first pair's triangulated joints; then all cameras refined together (triangulated joints reprojected, Cauchy loss, camera 2 kept at the measured distance). On the synthetic take (phones ~3 m from the middle, 2 px noise, each phone placing each joint ±1.5 cm differently, 3% swapped frames): cameras within 1.3–2.5 cm and 0.6°, a 30 ms sound error corrected by 27.5 ms, three cameras within ~6 cm; a focal length typed 3% off puts the cameras ~10 cm off |
| Show Video with several cameras (2026-11-03) | **One Movie Clip Editor per camera** (the user), stacked top to bottom in camera order next to the viewport, each video kept in step with camera 1 by its Sync offset and frame rate (the same clip the Blender phone camera shows behind it; Claude, after the user's two videos at 30.02 and 28.97 fps drifted 1.2 s apart over 35 s: Blender shows one clip frame per scene frame, so a clip at another rate gets a driver on its start frame, a simple expression that needs no Python auto-run, picking the frame filmed at that moment), the tracked skeleton drawn on each camera that has been captured. Calibration Start/End stay for both methods (the user); for Body they pick the walk-around inside a longer video |
| Multi-camera sync (2026-11-03) | **Audio, automatic** (the user): the soundtracks are matched (a clap at the start recommended), read with Blender's built-in `aud` module (checked on the user's clip: 48 kHz stereo as a numpy array); a per-camera offset field corrects it by hand. **Noise floor** (2026-11-04, Claude, a bug fix): sounds below 10× the take's median loudness make no onsets. On the user's near-silent take (−68 dBFS, one clap) the room hiss had made the sync 0.85 s wrong (a 2.2 s error on a test like it); now it finds the clap (+0.334 s, clear peak) |
| Multi-camera hardware (2026-11-03) | **2 phones** (the user), roughly 60–90° apart, both seeing the whole body; the design takes any number of cameras from 2 up |
| Multi-camera floor (2026-11-03) | **The board standing upright on the floor** for ~2 s, facing between the phones (the user). Replaces the first choice, the board lying flat: measured, a level phone framing a whole body sees the floor only from ~2.5 m, where a flat A4 board gives 0 corners even at 4K. Floor height = the paper's bottom edge (half the paper's leftover height below the squares, as the board is printed centred; paper size A4/Letter is a setting), up = the board's sides. A flat board is still used when a phone does see one. Found automatically: the board still for ≥ 1 s, flat (normal within 50° of the camera's up) or upright (sides within 50° of it), and the lowest such floor wins. Without one, the floor comes from the triangulated feet (to build) |
| Multi-camera solver input (2026-11-03) | **The same solver on triangulated 3D points** (the user); only its single-camera guesses (camera leveling, image-based foot contacts) get 3D versions |
| Depth fix order (2026-11-04) | **Multi-camera solve first, then a single-camera depth repair** (the user). Found on the user's take: MediaPipe's one-camera 3D folded the straight-standing body in depth (knees 31–36°, legs 14° slanted, body bend at the hips 14°, while the video's 2D points were straight within 1–4°) |
| Multi-camera solve (2026-11-04) | Details by Claude: camera 1's frames are the time base; each further camera's 2D points are read at the same moment (its Sync offset plus the calibration's picture delay, interpolated between its frames), lens distortion undone, frames where it swapped left and right (against camera 1) swapped back, then linear triangulation; a point is dropped where a camera sees it more than 3% of its picture height away from the triangulated point. **MediaPipe's visibility is not used**: its guesses for points it calls hidden agreed between the user's cameras within ~5 px (the webcam called the right elbow hidden on 95% of frames, which would have dropped the arm). Hands: triangulated relative to the wrist; where only one camera has a hand, that camera's MediaPipe hand turned into the world. The result goes to the unchanged solver as a landmark cache in a level camera-1 frame, torso leveling off (the calibration's floor is level). **All Cameras** checkbox in Solve (on by default); Capture captures every camera's video. On the user's take: body 99% of frames, cameras agreeing within 3 px; the solved whole body 2.8° from vertical (one camera: 10.3°), knees 9° / 6° (one camera: 36° / 33°) |
| Rig up axis (2026-11-04) | **The armature axis nearest to hips-to-head** (Claude, a bug fix): the user's rig has the head 4 cm ahead of the hips at rest, so up taken along that line leaned every solved pose 3.7° forward (one camera and several) |
| Single-camera leg repair (2026-11-04) | **Always on for one-camera solves, legs only** (the user): each leg joint on its camera ray at its bone's length, MediaPipe only choosing toward/away; lens from the panel's Lens setting. Measured on the user's phone take against the two-camera triangulation: shins within 2-5° (MediaPipe 23-25°); torso and arms got worse when repaired, so they keep MediaPipe's 3D. Insensitive to the Lens setting (18-50 mm for a 26 mm phone all far better than none). Lengths: 75th percentile (Claude: higher percentiles and a ray-distance refinement let jitter lengthen the bones and bent the knees again) |
| One-camera leveling (2026-11-04) | **By the whole body** (the user; replaces torso leveling): the median ankles-to-shoulders line goes straight up. The user's take has a real 8° bend at the hips that torso leveling turned into a leg slant. One camera now (leg repair + body leveling): phone whole body 4.6° from vertical (was 10.3°; two cameras 2.7°), knees 8° / 9° (was 36° / 33°); side webcam 6.5° (was 11.1°), knees 13° / 8° (was 19° / 11°). Known weak spot: a clip crouched, sitting or lying most of the time |
| Foot lock knee limit (2026-11-04) | **The lock may turn a knee at most 3° away from the tracked bend** (the user); the foot then stays that little off its target. Near a straight knee 7 mm of leg length cost 10° of bend (left knee 6° tracked, 16° locked on the user's two-camera take; now 9°). Cost there: ankles a median 0.5 cm, at most ~1 cm, into the floor; a median 1 mm of sliding while planted, 3 cm in the worst stretch. With one camera the misses are larger (up to ~3 cm, 5 cm) |
| Multi-camera UI (2026-11-03) | **A camera list in the panel plus a Blender camera per phone** (the user): video, sync offset, calibrated yes/no; Calibrate adds a camera at each phone's measured spot with its video as background, so Compare View can look through either. One video = today's single-camera workflow |

| Calibration reuse (2026-11-03) | Claude: the calibration file records its inputs (each video's name, size and modification time, sync offsets, square, paper, frames); Calibrate reuses it when they all match and calibrates again otherwise |
| Phone cameras (2026-11-03) | Claude: Calibrate adds or updates `FreeClipMocap Phone 1`, `… 2` (found by name) at the measured spots, lens and principal point from the calibration (lens distortion is not shown), each with its take video behind it, started later by its sync offset (whole frames); render size set to camera 1's video |
| Calibration storage (2026-11-03) | **JSON next to the videos** (the user): `<video folder>/FreeClipMocap/<first camera's video>.calibration.json`, reusable for other takes and .blend files |
| Calibration method (2026-11-03) | Chosen by Claude after tests on synthetic two-camera videos: each lens from up to 40 board views (focal length with square pixels, principal point at the centre, k1 and k2; frames off by 3× the median dropped), then both lenses refined together with the second camera's pose (OpenCV `stereoCalibrate`, up to 40 frame pairs): the lens alone was 2–3% off in focal length when the board stayed far away. The second phone's corners are interpolated to the first phone's frame times, so frames need not line up. Sound and picture can be a few tens of ms apart on a phone, so the board itself refines the sound offset within ±60 ms, on moving frames only (a still board shows no timing error). On the synthetic test: cameras within 0.5–1.8 cm and 0.5°, focal lengths within 0.6%, a sound offset 25 ms off corrected by 28.5 ms, about 1 s per calibration |
| World axes (2026-11-03) | Claude: Z up from the floor, Y = the first camera's view direction made level (the actor facing the first camera faces −Y, Blender's front), origin on the floor below where the cameras' view axes meet |

Confirmed by the user on a real clip: Blender stayed smooth |

Before the first good frame, the first good pose is held |
| Hand search (2026-11-03) | **A crop around each wrist, one hand tracker per hand** (the user), instead of searching the full frame (hands were found in 1–12% of the user's latest clip). Hands found: 88% / 49%. Captures redone once (settings field `hand_search`) |
| Finger joint limits (2026-11-03) | **Yes** (the user): each finger joint's rotation is split into curl (toward the palm), spread and twist, each clamped: base joints curl −30…95°, spread ±20°; middle −5…110°; end −10…90°; middle/end spread ±5°; thumb looser. Palm side from the thumb tip; a hand without a mapped thumb is not limited |

| Control rigs (2026-11-03) | **Solve switches the rig to FK** (the user): a preset may carry `rig_settings` (the rig's own sliders) that Solve applies and reports; Rigify's arms and legs go to FK (`IK_FK` = 1, measured: 1 = FK) and neck/head follow to 0. | Key reduction near planted feet (2026-11-03) | **Tighter tolerance for the hips and legs** (the user): 2° per bone let planted feet slide 6–8 cm; bones above a foot now get the tolerance that moves the foot by 0.2% of the hips-to-toe length. | Root motion (2026-11-03) | **"Root Motion" checkbox in Solve, off by default** (the user): off = in place like Mixamo's "In Place" clips (the hips still move up/down, lean and sway; only travel by stepping is taken out); on = the body travels as in the video. | Foot locking (2026-11-03) | **Planted feet locked with two-bone leg IK** (the user): no foot sliding while planted; knees adjusted to reach, blended in/out over 3 frames. Details chosen by Claude: planted = heel and toe nearly still in the image (static camera) and not lifted above the other foot; floor = the rig's own rest-pose foot height, up snapped to the nearest armature axis; the hips are lowered only when a straight leg cannot reach its planted foot |
| Planted feet flat (2026-11-04) | **A planted foot is turned flat on the floor** (the user): its rest-pose tilt, MediaPipe's heading kept, blended in and out with the lock. Found on the user's two-camera take: MediaPipe tipped the planted feet 15–22° (heel and toe depth is poor from one camera), and putting the tipped foot's lowest point on the floor lifted the ankle ~9 cm, so the knee bent a median 22° more than MediaPipe's. Flat: the lock adds a median 0° (99th percentile 11°); the rest comes from MediaPipe's two legs reaching ~1.3 cm apart while both feet are planted. MediaPipe's own 3D knees stay bent 22–36° on that take even where the leg looks straight in the video (depth again); left to the multi-camera solve |
| IK/FK switch (2026-11-04) | **IK controls with a live, keyable IK/FK slider per limb, legs and arms** (the user). Details by Claude: Add IK Controls makes a target empty (foot/hand, keyed to the solved position and rotation) and a pole empty (knee in front, elbow behind) per limb, parented to the armature in an `<armature> IK Controls` collection; an IK constraint (chain 2, no stretch) on the shin/forearm and a Copy Rotation on the foot/hand, their influence driven by the armature's custom property `IK Left Leg` etc. (0 = FK, 1 = IK). The pole angle is fixed from the upper bone's own bend axis and the pole is placed across the root-to-target line, which is how Blender's IK reads it, so IK at 1 reproduces the FK take within 0.25° and 1 mm on the user's rig (a pole simply in front of the knee was up to 9° off on the arms). The armature is never changed; FBX and BVH export the evaluated pose, so IK edits are exported. Solve mutes the IK while writing and keys the targets to the new take; Match IK to FK keys them again; Remove IK Controls can bake the pose into the FK keys first (only limbs IK actually changed) |
| Video frame range (2026-11-03) | **Solve only** (the user): capture tracks the whole video once; Solve uses the chosen frames. | Purpose of the result (2026-11-03) | The animation is a **starting point that the animator corrects by hand** (the user). Keyframes must be easy to edit |
| Solver output choices (2026-11-03) | Left to Claude by the user ("do what's best for users; I'm not an animator"). **Rotation mode:** each bone's own (quaternion keys for quaternion bones, Euler with continuity for Euler bones); the rig is never changed. **Keys:** one per scene frame first; key reduction (on by default, ~0.5° tolerance) added after the first visual review. **Timing:** resampled to the scene's frame rate, keys on whole frames from the scene start; the scene end is set to the take's end. **Smoothing:** One Euro filter on the landmarks, one 0–1 slider, default 0.5. **Gaps:** hold the last good pose; before the first good frame, the first good pose. **Hips:** rotation only in Phase 1 (in place); root motion in Phase 2 |

| Creating objects (2026-11-03) | Simple data objects are constructed directly; when building does real work, a named `@classmethod` does it (`BoneMap.guess_from_armature(...)`, `LandmarkCache.load(...)`). Changes of state through named methods |
